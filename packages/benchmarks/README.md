# benchmarks

Not a real package, and never published: like `integration`, the name sits
outside the `without*` family the publish workflow globs, and a `Private :: Do
Not Upload` classifier makes PyPI reject it as a backstop. It is where the
whole stack is put under load and compared, apples-to-apples, against a peer
framework.

## What it measures, and why the shape

The bet is that a benchmark should isolate *one* variable at a time. So the two
stacks under test share the same functional core and differ only at the edges:

- **Same core.** Both shells import the pure `integration.todos.core`
  (`TodoList`, `NewTodo`, `Todo`). The domain logic (parse a body, fold the
  immutable list, render a todo) is byte-for-byte identical, so a measured
  difference is framework + server overhead, not business logic. `apps.py` holds
  the two shells: `without_todos()` is the `without-web` app (via `integration`),
  `fastapi_todos()` is the idiomatic FastAPI equivalent. Neither persists past a
  request (create echoes the would-be todo), matching `integration`'s stance so
  both do the same work per request.
- **Whole stack, real socket.** `servers.py` runs each shell as a long-lived
  server process, *as it would actually be deployed*: the without app on
  `without-http` over stdlib `asyncio`; the FastAPI app on `uvicorn` with
  `uvloop` + `httptools`. The load crosses a real TCP socket, not an in-process
  shortcut. (The event-loop difference is deliberately *not* controlled away:
  this compares the stacks people actually ship.)

## Methodology

- **The load generator must be far cheaper than the server**, or the two get
  conflated. So load is generated by [`vegeta`](https://github.com/tsenart/vegeta),
  a compiled (Go) tool in a *separate process*. Nothing in this package's
  interpreter is on the measurement path; the async `harness.py` only supervises
  (it even gates server readiness through `without-http`'s own client, dogfooding
  the client against the server under test).
- **Open loop, to defeat coordinated omission.** A closed-loop generator (fixed
  connections, each sends → waits → repeats) stops issuing while the server
  stalls, so the worst-case latencies never enter the sample and the tail looks
  artificially healthy. vegeta drives a *constant arrival rate* (`-rate`)
  decoupled from responses, so its latency distribution reflects reality.
- **A rate sweep, not one number.** The deliverable is a latency-vs-throughput
  curve: run several `--rate` steps and read where each stack's tail (p99/p99.9)
  knees over. A single point can't show that. The optional `--saturate` run is a
  deliberately over-capacity step; read it as a *throughput ceiling*, not as a
  latency figure.
- **Sampling profiler on the server, per rate.** With `--profile`, each rate's
  server is launched *under* the
  [`austin`](https://github.com/P403n1x87/austin) statistical sampler (no
  instrumentation of the hot path). Launch mode, rather than attaching to a PID,
  means austin is the server's parent, so it works under the common Yama
  `ptrace_scope=1` with no sudo. Each rate gets its *own* profile, since the hot
  path can look different under light load versus past the knee. austin 4.0 emits
  the MOJO binary format, which the harness converts to a speedscope flamegraph
  via `austin-python`'s `mojo2austin` then `austin2speedscope`. This is the
  stand-in for CPython 3.15's stdlib `profiling.sampling`, which the project can
  adopt once it moves off 3.14.

## Prerequisites

The Python side comes from `uv` (including `austin2speedscope`, via the
`austin-python` dependency). The two *binaries* are managed by
[`mise`](https://mise.jdx.dev/) from the repo-root `mise.toml`:

```bash
mise install        # austin (sampler) + vegeta (load generator)
```

Because the harness launches the server *under* austin (rather than attaching to
a running PID), `--profile` needs no `ptrace` relaxation. austin is pinned to 4.0
for Python 3.14 support; the run leaves a `.mojo` (raw samples), an intermediate
`.austin`, and the `.speedscope.json` flamegraph per rate.

## Running

```bash
# Sweep the without stack's list endpoint across the default rates.
uv run python -m benchmarks.harness without --endpoint list

# The FastAPI peer, the write path, custom rates, and a saturation ceiling,
# with a flamegraph of the server.
uv run python -m benchmarks.harness fastapi --endpoint create \
    --rate 2000 --rate 8000 --saturate 40000 --profile
```

Results land in a git-ignored `results/`, named
`{stack}-{endpoint}-r{rate}-d{duration}s[-prof]`, so a profiled run and a clean
one (or two durations) at the same rate coexist rather than overwrite. Each run
leaves a `.bin` (raw vegeta) and `.txt` (report); `--profile` adds the `-prof`
tag and a `.speedscope.json` flamegraph. Endpoints: `list` (`GET /todos`), `show`
(`GET /todos/2`), `create` (`POST /todos`).

`just plot` reads the *clean* (non-`-prof`) runs and draws latency and throughput
versus target rate to `results/{endpoint}-latency-throughput.png`.
